How it works

A Fabric tenant acts as one catalog. DuckDB runs on your machine in a process of its own, reads OneLake directly with your own token, and keeps what it reads.

One name per object

Everything else depends on this. A name is where Fabric keeps the object, with its type moved to the front.

ObjectIts nameExample
A table<kind>.<workspace>.<item>.<schema>.<table>lakehouse.aemo.data.dbo.dim_duid
A semantic modelsemanticmodel.<workspace>.<model>semanticmodel.aemo.nem
A file'lakehouse.<workspace>.<item>/Files/<path>''lakehouse.aemo.data/Files/x.parquet'

Fabric guarantees that a workspace's name is unique in the tenant, an item's name is unique for its type in a workspace, and a table's name is unique in its schema. So a name means exactly one object, which is what makes a join across workspaces safe. If a name could mean two objects, a query could read the wrong data with no error.

Five parts are real SQL, not a parser trick. The kind is a DuckDB catalog, the workspace, item and schema are schemas nested inside it, and the table is a view over iceberg_scan of its current metadata.

How the parts fit

Tree, tabs and command line
The ways in. A tab is a view: it holds no token and makes no network request. The command line hands its arguments to the running extension.
Window
One extension host per VS Code window. It holds the sign-in and the read-only guard, resolves names to tables, and keeps the catalog current in the background.
Catalog
A SQLite file that holds all metadata: listings, table metadata, the models opened, and what has been read. The tree draws from it before sign-in, with no server running and no DuckDB loaded.
Server
DuckDB 2.0, running natively in a process of its own, one per account and install. Every tab of every window is a client of it over DuckDB's Quack protocol, and they share one memory budget and the blocks read.
OneLake and the Fabric REST API
A table is read with iceberg_scan on the metadata file the cache holds, so the catalog is never asked at query time. Semantic models come from the Fabric REST API, which needs a second token. VS Code's Microsoft account provider gives both, with no app registration.

How the parts fit and the server, in full

What happens when a statement runs

  1. Open the models it names. The host opens each semanticmodel.<ws>.<model> not open yet from its local copy, reading it from Fabric the first time.
  2. Compile. dax-sql rewrites a model query as plain SQL over five-part table names. A statement that names no model passes through unchanged.
  3. Check. The host refuses more than one statement and anything that isn't a read, then asks DuckDB's own parser what the statement is.
  4. Prepare. The engine makes a view for each five-part name, from the cached listings, and gives DuckDB each file's abfss:// URL in place of its name. A name that can't be found fails here.
  5. Run. The statement goes to the server, and its tab's Stop reaches only that tab's statements. A result past maxResultRows, 200,000 by default, is counted rather than carried into the tab.

The rules every change keeps

RuleWhat it means
One name per objectA table has five parts and a model has three. A file is its lakehouse's name and its path under Files/.
SQL onlyA model is read with AGG("measure") in SQL. There is no DAX query.
Read onlyNothing is written to Fabric or OneLake. The one exception is Export to Fabric, after an OK in VS Code.
Cache firstEvery answer from OneLake or Fabric is kept on this machine and served from there first. It is trusted until using it fails, then read again once.
Works offlineA feature that reads data works from what this machine holds, with no network. What isn't held says so at once, never on a timeout.
The host does the workSign-in, the read-only guard, and OneLake's listings and metadata are in the host, and DuckDB's reads are in the server it starts.

Offline and the cache

Offline is a requirement, not a fallback, and nothing turns it on. The extension is offline when there is no internet or no session, says which in the status bar, and comes back by itself. No request is sent, so nothing waits on a timeout.

Works offline, if cachedNeeds OneLake
The tree, SHOW ALL TABLES, information_schema, Go ToA column or a file never read
A table's Stats and History, and first rows already readA wildcard over files
Semantic models: opening them, Explore's Model page, SHOW SEMANTIC …A table whose metadata was never read
Table rows, a model's queries and its Pivot, for what was readExport to Fabric
Files/ objects read before

Metadata is kept in the catalog file. The bytes DuckDB reads are kept in its disk cache, cache_httpfs, and are read again only when a file was rewritten. The cache is per Microsoft account, so switching accounts never serves one account's data to another. It survives a sign-out, and only Clear Cached OneLake Data deletes it.

Semantic models

A Power BI semantic model is a Fabric item, not a file in OneLake. In SQL it is a semantic view, read as one table:

SELECT dim_region.Region, AGG("Registered MW") AS mw
FROM semanticmodel.aemo.nem
GROUP BY ALL;

Opening a model reads its definition from the Fabric REST API and keeps it on this machine, so later opens ask Fabric nothing. dax-sql compiles its measures to SQL, and DuckDB reads the tables behind them from the lakehouse the model names. Only Direct Lake is supported, over OneLake or a SQL endpoint, whose tables are read from OneLake all the same, and reading a definition needs Contributor or above on the workspace, or write on the model.

Agents

An agent gets the same access as a person. The command line asks the running extension over a local pipe or socket, and the extension answers with its own sign-in, cache, engine and compiler, so VS Code must be open and signed in. Install Agent Skill sets it up for Claude Code and GitHub Copilot in VS Code.

The answer alone goes to stdout and notes go to stderr. --json gives a structured answer, and exit codes say what happened, such as 3 for VS Code not open or not signed in, and 4 for not cached.

Out of scope

  • DAX queries (EVALUATE).
  • Writing to OneLake, DDL, or editing data in the grid.
  • CREATE and DROP SEMANTIC VIEW: a model exists because Fabric has it, not because SQL made it.
  • A TDS connection to the SQL endpoint.
  • ER diagrams for lakehouse tables: they declare no keys.
  • vscode.dev: the engine is a native library, so this needs desktop VS Code.
